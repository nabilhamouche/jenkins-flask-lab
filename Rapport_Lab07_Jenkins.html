1. Introduction

The goal of this lab is to automate the build, test and deployment of a small Flask application using Jenkins, Docker and GitHub. The code and the Jenkinsfile live in GitHub; Jenkins reads the Jenkinsfile, builds a Docker image tagged with the build number, runs the tests inside that image, deploys the container on port 8081 and finally checks that the application answers over HTTP.

Workflow: GitHub → Jenkins Pipeline → Docker Image → Docker Container → Flask Application

2. The application

The Flask app (app.py) exposes two routes: / shows the title and the version (environment variable APP_VERSION, set to the Jenkins build number), and /health returns {"status":"ok"}. Two pytest tests (tests/test_app.py) check both routes. The Dockerfile (python:3.12-slim) installs the dependencies, copies the app and tests, and starts the app with gunicorn on port 8000. Inside the container the app listens on 8000; Docker maps it to port 8081 of the host.

Correction to the lab handout: in the PDF the Jenkinsfile variables were garbled by the export (e.g. "IMAGE_NAME:{BUILD_NUMBER}"); the correct form is ${IMAGE_NAME}:${BUILD_NUMBER} and -p ${APP_PORT}:8000 -e APP_VERSION=${BUILD_NUMBER}. Also, the test command was changed from pytest -v to python -m pytest -v: with plain pytest the working directory is not on Python's import path and the test fails with ModuleNotFoundError: No module named 'app' (observed when running the image). python -m pytest adds the current directory to the path.

6. Answers - Blue-Green deployment (Section 19)

  1. Deployment vs release: deployment puts a version on infrastructure (technical action); release makes it available to users (business decision). A version can be deployed without being released.
  2. Why deploy to Green first: to test and validate the new version in a production-like environment without exposing users to possible bugs.
  3. Routing component: a reverse proxy / load balancer such as NGINX.
  4. Why keep Blue: so traffic can be switched back immediately if Green shows problems.
  5. Jenkins automation: a pipeline with stages Build, Test, Deploy Green, Validate (smoke tests), an input step for manual approval, then a stage that updates the proxy configuration to switch traffic.
  6. Main benefit of rollback: fast, low-risk recovery with minimal downtime, since the previous version is still running.

7. Answers - Questions (Section 20)

  1. Jenkins: an open-source automation server for CI/CD. It removes manual, error-prone build/test/deploy work by running them automatically and consistently.
  2. Jenkinsfile: a text file stored with the code that defines the pipeline as code (versioned, reviewable, reproducible).
  3. CI vs CD: Continuous Integration automatically builds and tests every change merged into the shared repository. Continuous Delivery keeps the software always in a deployable state and automates delivery to environments, with release usually triggered by a (manual) approval.
  4. GitHub: hosts the source code and the Jenkinsfile; Jenkins clones it for every build and it provides version history.
  5. Docker: packages the app and its dependencies in an identical, isolated environment, so build, test and run behave the same everywhere; images are tagged per build.
  6. Tests before deployment: to detect defects early and stop broken versions from reaching the running application.
  7. Failed stage: the pipeline stops, the build is marked FAILED, later stages are skipped and the post-failure actions run.
  8. Verify stage: confirms that the deployed container actually runs and answers HTTP requests (/health and /), i.e. that the deployment really works.
  9. Credentials in a Jenkinsfile: the file is in the repository, so passwords/tokens would be exposed to everyone with access and kept in history. They must be stored in the Jenkins Credentials store and referenced by ID.

8. Conclusion

The pipeline automates the full path from commit to a verified running container, and the failure experiment shows that the Test stage acts as a quality gate protecting the deployed version. Security note: giving Jenkins access to Docker is equivalent to broad control of the host, so it should only be done on an isolated lab machine.
